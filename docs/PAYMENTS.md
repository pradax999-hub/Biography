# Оплата: как устроено и как включить

## Коротко

- Карты принимаются через **Stripe Checkout**: клиент вводит карту на странице
  Stripe, этот сайт данных карты не видит и не хранит.
- Заказ считается оплаченным только после подтверждения сервером: по
  подписанному вебхуку Stripe или по прямому запросу сервера к Stripe.
  Адрес возврата в браузере ничего не доказывает и ни на что не влияет.
- Без ключей Stripe оплата картой просто не показывается. QR-перевод, ссылка
  и «в чате» работают как в 1.0.
- **Живые платежи сейчас не включены.** Они заработают только после шагов из
  раздела «Включение Stripe».

## Почему Stripe

В 1.0 платёжного провайдера не было (см. `docs/AUDIT.md`), поэтому выбирать
пришлось с нуля. Доводы:

- работает в Чехии (счёт для QR-перевода чешский, в кронах), принимает
  оплату в долларах и выводит в кронах;
- готовая страница оплаты на стороне Stripe: карты, Apple Pay, Google Pay;
- полноценный тестовый режим с тестовыми картами;
- подписанные вебхуки и ключи идемпотентности;
- хорошо сочетается с Netlify Functions, где уже живёт сайт.

Альтернативы: чешские шлюзы GoPay и Comgate (обычно нужен IČO), PayPal
(его можно подключить уже сейчас через `payLink` в `src/config/site.ts`,
но без автоматического подтверждения). Условия и комиссии у всех меняются:
сверься с их сайтами перед выбором.

> **Важно про возраст.** Аккаунт Stripe может открыть только
> совершеннолетний. Его должен оформить родитель или законный представитель
> на себя, как уже сделано со счётом для QR-перевода. Заодно стоит уточнить у
> него, какие правила приёма оплаты действуют для владельца счёта.

## Как проходит заказ

```
браузер                     сервер (/api)                    Stripe
   │  POST /api/orders          │                               │
   │ ─────────────────────────► │ проверяет поля, сам считает   │
   │                            │ цену, сохраняет заказ,        │
   │  номер заказа + токен      │ шлёт уведомление в Telegram   │
   │ ◄───────────────────────── │                               │
   │  POST …/checkout           │                               │
   │ ─────────────────────────► │ создаёт Checkout Session ───► │
   │  адрес страницы оплаты     │                               │
   │ ◄───────────────────────── │                               │
   │  клиент платит на странице Stripe ───────────────────────► │
   │                            │ ◄── вебхук с подписью ─────── │
   │                            │ проверяет подпись, сумму,     │
   │                            │ валюту → статус «оплачен»     │
   │  возврат на сайт           │                               │
   │  GET /api/orders/:id       │                               │
   │ ─────────────────────────► │ если вебхук ещё не пришёл,    │
   │  статус                    │ спрашивает Stripe напрямую    │
   │ ◄───────────────────────── │                               │
```

Статусы заказа: `created` → `awaiting_payment` → `paid`, а также `pending`
(платёж принят, деньги ещё не зачислены), `failed`, `cancelled`, `expired`.

## Что защищено

| Риск | Что сделано |
| --- | --- |
| Подмена суммы в браузере | Сервер считает цену сам из `shared/catalog.ts`. Любые суммы из запроса игнорируются. |
| Поддельное «оплачено» | Статус меняют только подписанный вебхук или ответ Stripe серверу. Сумма и валюта сверяются с заказом; при расхождении заказ помечается и владельцу уходит уведомление. |
| Поддельный вебхук | Проверка подписи (`STRIPE_WEBHOOK_SECRET`), допуск по времени. |
| Повторная доставка вебхука | Номера событий запоминаются, повтор не меняет ничего. |
| Двойная оплата | Оплаченный заказ нельзя отправить на оплату снова; открытая сессия переиспользуется; перед новой попыткой старая сессия закрывается; у каждого запроса к Stripe свой ключ идемпотентности. |
| Чтение чужого заказа | Нужен секретный токен, который получает только браузер заказчика; в хранилище лежит его хэш. Ответ «нет заказа» и «не твой заказ» одинаков. |
| Утечка ключей | Ключи есть только в переменных окружения сервера. В браузер уходит лишь «оплата включена: да/нет, режим тестовый/боевой». |
| Спам заказами | Ограничение частоты, скрытое поле-ловушка, лимиты длины. |

Хранится только то, что ввёл клиент (имя, контакт, описание, референс),
расчёт и история статусов. IP-адреса и данные карт не хранятся.

## Песочница (без аккаунта)

`npm run dev` включает её сам. Вручную: `PAYMENT_PROVIDER=sandbox` и
`SANDBOX_WEBHOOK_SECRET=<случайная строка>`.

Кнопка «Оплатить» ведёт на страницу-симулятор с пометкой TEST. На ней можно
разыграть успешную оплату, отказ, зависший платёж (и затем его исход), отмену
и подмену суммы. Каждый вариант отправляет сайту подписанный вебхук тем же
путём, что и настоящий провайдер. Деньги не движутся. Не включай песочницу на
боевом сайте: любой сможет «оплатить» заказ.

## Включение Stripe

1. Владелец счёта регистрируется на stripe.com и проходит проверку.
2. **Developers → API keys.** Сначала возьми тестовый ключ `sk_test_…`.
3. **Developers → Webhooks → Add endpoint.**
   - Endpoint URL: `https://ТВОЙ-САЙТ/api/webhooks/stripe`
   - События: `checkout.session.completed`,
     `checkout.session.async_payment_succeeded`,
     `checkout.session.async_payment_failed`, `checkout.session.expired`
   - После создания скопируй **Signing secret** (`whsec_…`).
4. В Netlify: **Site configuration → Environment variables**
   ```
   PAYMENT_PROVIDER=stripe
   STRIPE_SECRET_KEY=sk_test_…
   STRIPE_WEBHOOK_SECRET=whsec_…
   SITE_URL=https://ТВОЙ-САЙТ
   ```
   Публичный ключ (`pk_…`) не нужен: страница оплаты открывается по ссылке.
5. Передеплой сайт и открой `/api/health`: должно быть
   `"payments":"stripe","mode":"test"`.
6. Сделай тестовый заказ картой `4242 4242 4242 4242` (любая будущая дата,
   любой CVC). Отказ: `4000 0000 0000 0002`. Проверь, что статус на сайте
   стал «Оплачен», а в Stripe у вебхука ответ 200.
7. Боевой режим: создай **отдельный** вебхук в боевом режиме Stripe, поставь
   `sk_live_…` и новый `whsec_…`, передеплой, проведи один настоящий платёж
   на небольшую сумму и верни его.

Локальная проверка вебхуков со Stripe CLI:
`stripe listen --forward-to localhost:5173/api/webhooks/stripe`
(CLI напечатает `whsec_…` для `.env`).

## Ручные оплаты (QR, ссылка, чат)

Перевод по QR сайт проверить не может. Когда деньги пришли, отметь это в
**панели владельца**: открой `https://ТВОЙ-САЙТ/api/admin`, введи
`ADMIN_TOKEN` и нажми «Оплата получена» у нужного заказа. Клиент увидит
статус «Оплачен» на своей странице заказа.

В панели видны все заказы, их статусы, контакты клиентов, история событий и
три индикатора настройки: оплата картой, Telegram, хранилище. Страница
отдаётся сервером без скриптов; токен нигде не сохраняется в браузере.
Для карточных заказов кнопки «Оплата получена» нет: их подтверждает только
платёжный сервис.

Пока `ADMIN_TOKEN` не задан, панели и адресов `/api/admin/*` не существует.
Придумай длинную случайную строку, например `openssl rand -hex 32`.

То же самое доступно как JSON API (для скриптов):

```sh
curl https://ТВОЙ-САЙТ/api/admin/orders -H "Authorization: Bearer $ADMIN_TOKEN"

curl -X POST https://ТВОЙ-САЙТ/api/admin/orders/NW-261113-1234/status \
  -H "Authorization: Bearer $ADMIN_TOKEN" -H "Content-Type: application/json" \
  -d '{"status":"paid","note":"перевод получен"}'
```

## Что проверено, а что нет

Проверено тестами в этом репозитории:
- расчёт цены, проверка полей, жизненный цикл заказа, подписи, идемпотентность
  панель владельца, заголовки безопасности (`npm test`, 79 тестов);
- весь путь в браузере через песочницу: успех, отказ и повтор, отмена,
  зависший платёж, подмена суммы (`npm run test:e2e`, 99 проверок);
- код Stripe: создание сессии и разбор вебхуков на поддельном HTTP-клиенте,
  подписи сгенерированы собственным помощником Stripe SDK.

**Не проверено** (нет ключей и доступа): настоящие запросы к Stripe,
настоящая доставка вебхуков, работа на Netlify с хранилищем Blobs, доставка
сообщений в Telegram. Это первое, что нужно прогнать после настройки.
